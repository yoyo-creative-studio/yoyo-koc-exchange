我独立开发了一套 KOC 创作者管理系统。

它已经用于管理创作者注册、作品提交、积分结算、奖励兑换、奖励发放和日常问题回复。

真实业务正在使用
01 · 为什么要做

创作者一多，所有事情都压在我的私信和 Excel 里。

从催交作品、收链接、算分、通知结果，到兑换、改订单和追物流，都靠我逐个私聊、逐格登记。即使只有十几位创作者，也可能要打开几十到上百条作品链接，完整结算会连续占用数天。

收私信复制链接打开作品抄数据算分回填 Excel私信结果
01每条作品都要人工取数我逐个打开 Facebook、TikTok、Instagram 等作品，抄下播放、点赞或互动数据，再按不同平台规则计算积分。
02多张 Excel 反复对人投稿、身份、积分、兑换和发奖各有表格。Discord 改名、同名、重复链接或月份填错，都要回头重新核对。
03通知和修改全靠私聊结算结果逐个发送；少分、补分、改奖励、改地址继续在私信里处理，重要信息很容易被新消息冲走。
04发奖还要再登记一遍礼品卡、端内奖励和实体周边由不同流程发放。订单、积分扣除、物流号和收件人需要再次手工匹配。
02 · 我想解决什么

把依赖我个人记忆和私信的工作，变成创作者可以自己完成的流程。

创作者提交作品后，系统知道她是谁、提交哪个月、应该按什么规则计算；积分确认后，她能自己查看余额、兑换奖励和追踪发放进度。我不再负责复制、搬运和逐个通知，只处理内容审核、异常数据和需要业务判断的问题。

03 · 系统包括什么

四个入口，共用同一套身份、业务规则和数据。

对创作者，它是可以自助注册、投稿、查分和兑换的门户；对运营，它是覆盖审核、算分、通知和发奖的管理后台；Bot 把验证码、个性化通知和客服带回 Discord；底层数据库负责把每个人、每条作品、每次积分变化和每笔订单串在一起。四端不是各做一张表，而是围绕同一个 Creator ID 读写同一份业务记录。

👩‍🎨创作者门户
创作者本人使用的前台，把原来散落在 Google Form、Excel 和私信里的操作集中起来。
  • 功能：注册、Discord OTP 登录、投稿、查分、等级、兑换与物流查询
  • 前端：原生 HTML / CSS / JavaScript，响应式页面
  • 部署：GitHub Pages；只开放本人有权读取和提交的数据
🗂️运营管理后台
管理员处理需要判断、批量操作或跨创作者查看的工作，不再回到多张 Excel。
  • 功能：注册审核、作品审核、积分导入、等级管理、奖励发放与审计
  • 权限：Platform Owner / Admin / 项目隔离，多管理员按项目授权
  • 部署：静态管理界面 + Vercel 服务端代理，敏感操作不在浏览器暴露密钥
🤖Seraphina's Bot
Discord 里的业务入口，不只群发固定话术，还能识别创作者并查询她本人的实时状态。
  • 功能：登录验证码、审核通知、积分结算、物流推送和连续客服对话
  • 运行：Node.js + discord.js；连接知识库、模型接口和业务数据库
  • 边界：可以解释和查询，修改积分、订单或补偿仍交给管理员确认
☁️数据与服务层
系统的唯一数据来源，保证门户、后台和 Bot 看到的是同一个人、同一笔积分和同一个订单。
  • 数据：Supabase PostgreSQL，保存身份、作品、积分流水、订单和操作日志
  • 接口：REST / RPC / Edge Functions，处理认证、注册审核和 Discord 调用
  • 安全：Supabase Auth、RLS、服务端密钥隔离、项目权限与审计记录
04 · 最大的产品优势

发现问题的人，也是决定规则和开发功能的人。

传统平台要服务很多项目，一个一线问题要经过提需求、评审和排期，最后做出的通常只能满足共性需求。我同时负责运营、数据、规则、产品和开发，可以在真实工作里发现问题，马上做出贴合当前项目的功能，再把验证有效的能力做成配置和模块。

传统通用平台

问题要跨多个岗位传递

运营发现问题整理 PRD产品技术评审等待排期开发测试上线

周期可能以周或月计算；传递过程中会损失业务细节。为了适配所有项目，个别游戏的特殊规则只能继续靠人工。

这套系统

真实问题直接进入产品

我在运营中发现问题当天确认规则直接开发真实数据测试下个业务周期使用

没有需求转述，也不用等别人的排期。功能先解决眼前真实问题，稳定后再抽成权限、配置和项目模块。

兑换私信没人回改为创作者自助兑换，并允许 Pending 订单自行修改。
物流号容易配错人增加匹配预览和确认步骤，再发布到创作者前端。
反复询问本人进度让 Bot 识别身份并查询本人积分、订单和物流状态。
Discord 改名后登录失败增加 OTP、User ID 同步和历史别名匹配。
平台 API 被收回不用等待新接口，改用浏览器 Skill 直接核验原作品。
补分记录容易混乱把积分拆成独立流水，保留原因、月份和修改记录。
不是只做一个项目的临时工具：先用高度贴合的功能解决真实问题，再把稳定能力抽成可配置、可授权、可复用的平台模块。
05 · 跨平台算分 Agent

不让创作者交截图。我让 Agent 直接打开原作品取数。

我把七八个平台的页面结构、短链还原、登录态、反爬限制、取数字段、计分规则和失败处理写成可重复执行的 Skill。Agent 批量访问原链接，返回原始数据、得分和异常项；我只处理内容有效性和特殊情况。

这不是“让 AI 看一眼网页”

每个平台的数据藏在不同位置，还必须确认读到的是目标作品，而不是推荐内容、主页汇总或页面里的其他数字。

01 · 标准输入Creator ID、平台、原链接、月份、作品类型
02 · 平台取数还原短链、定位目标作品、读取公开指标
03 · 防误读核对作品 ID，排除推荐帖和页面杂项数字
04 · 断点续跑限速、分批、失败重试，不因单条失败重跑整批
05 · 规则计算按平台指标、当月门槛和封顶规则计算
06 · 可审计输出原始数据、得分、失败原因和异常清单进入 JSON

06 · AI 客服

Bot 可以根据创作者本人的数据回答问题。

例如创作者询问奖励进度时，Bot 会查询她自己的订单。涉及修改积分、修改订单或补偿时，交给管理员处理。
