01 / 背景与痛点

创作者规模扩大后，人工运营方式已经无法继续支撑。

KOC 业务最初依靠 Discord 私信、Google Form 和多份 Excel 运转。随着创作者、投稿和奖励数量增加，信息分散、重复核对和状态不透明开始直接影响月度结算效率与创作者体验。

01

信息入口分散

身份资料、收货信息、作品链接和积分记录散落在私信、表单与不同版本的表格中，难以确认哪份数据才是最终口径。

02

投稿容易遗漏

链接可能重复、粘连、归错月份或无法访问；运营需要逐人核对，创作者也无法确认作品是否成功收录。

03

结算与履约割裂

积分、钻石、Google Play 礼品卡和实体周边分别维护，订单状态、扣分时间和发放结果缺少统一追踪。

04

重复沟通成本高

投稿提醒、个性化算分结果、兑换进度和物流问题均依赖人工私信，人数增长后无法稳定服务。

02 / 项目目标

先跑通真实业务，再把一次性系统抽象为可复用平台。

系统既要稳定承接 MLT 的月度运营，也要让其他游戏或地区能够在不修改代码的情况下创建独立项目、配置规则并安全上线。

GOAL 01

统一数据入口

将注册资料、作品、积分流水、订单与履约结果集中管理，以不可变 Creator ID 建立稳定身份关系。

GOAL 02

建立月度闭环

让每个活动月都能够按固定流程完成开放、投稿、审核、结算、兑换、发奖和复盘。

GOAL 03

项目级数据隔离

同一个平台承载多个项目，但创作者、积分、投稿、订单和履约记录不可跨项目串联。

GOAL 04

配置化复制上线

通过模板、品牌、奖励、活动和上线检查，让新项目从创建到独立门户不再依赖开发改代码。

03 / 解决方案

以统一活动月为主线，连接创作者端和管理端。

我没有继续叠加更多人工表格，而是重新梳理完整业务链路：创作者负责提交和查询，管理员负责审核与履约，Supabase 保存业务事实，MochiBot 承担必要通知。

01

注册申请

统一收集身份、区服与履约资料。

02

人工审核

批准后激活账号并建立欢迎周边。

03

月度投稿

作品进入管理员指定的活动月份。

04

作品审核

按平台、数量和状态集中处理。

05

积分结算

通过 UID 导入确认后的算分结果。

06

个性化通知

每位创作者只收到自己的结算内容。

07

自主兑换

创作者查看余额并提交一种奖励。

08

奖励履约

发放结果公开，确认后完成扣分。

04 / 项目结果

从单一业务工具升级为经过真实业务验证的平台基础。

系统持续承接生产运营，同时完成项目边界、不可变身份、配置复制、独立门户、上线门禁和项目级权限改造，验证了多项目扩展不需要复制整套代码或共享最高权限。

RESULT 01

生产链路保持稳定

历史创作者、投稿、积分、兑换与履约记录在身份迁移后保持完整关联。

RESULT 02

项目数据真正隔离

同一 Game UID 可存在于不同项目，沙盒积分和配置修改不会影响生产项目。

RESULT 03

新项目可以复制

品牌、奖励和活动规则可事务化复制，人员、地址、投稿、积分和订单明确排除。

RESULT 04

上线风险被系统约束

新项目默认暂停，未完成配置时数据库拒绝激活，避免空规则或错误入口直接开放。

RESULT 05

管理权限可以安全交接

五级角色按项目授权，服务端拒绝跨项目操作；Platform Owner 不能被停用、删除或降级。

05 / 个人贡献

从业务负责人到产品架构与全栈开发，独立推动真实系统平台化。

我不仅把需求做成页面，还负责业务建模、规则定义、数据迁移、生产修复、架构演进与上线验证，并将每次真实问题沉淀为可复用的产品能力。

我解决了什么

把 Discord、Google Form、Excel 和人工台账拆解为可执行的业务状态机；进一步识别单项目系统的身份、配置、共享密码与浏览器密钥耦合，以 Creator ID、Project ID 和分级管理员身份建立稳定的数据所有权与责任边界。

我如何落地

采用渐进式迁移保护生产数据：先扩展项目边界，再回填与审计身份关系，最后替换旧主键和 RPC；通过沙盒验证多项目隔离后，实现带有效期会话、五级角色、项目授权、最高权限保护、服务端越权拦截，并将 Discord Token 迁移到按项目隔离的服务端密钥。
