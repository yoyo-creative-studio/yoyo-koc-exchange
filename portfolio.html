01 / 背景与痛点

创作者规模扩大后，人工运营方式已经无法继续支撑。

KOC 业务最初依靠 Discord 私信、Google Form 和多份 Excel 运转。随着创作者、投稿和奖励数量增加，信息分散、重复核对和状态不透明开始直接影响月度结算效率与创作者体验。

01

信息入口分散

身份资料、收货信息、作品链接和积分记录散落在私信、表单与不同版本的表格中，难以确认哪份数据才是最终口径。

02

投稿容易遗漏

链接可能重复、粘连、归错月份或无法访问；运营需要逐人核对，创作者也无法确认作品是否成功收录。

03

结算与履约割裂

积分、钻石、Google Play 礼品卡和实体周边分别维护，订单状态、扣分时间和发放结果缺少统一追踪。

04

重复沟通成本高

投稿提醒、个性化算分结果、兑换进度和物流问题均依赖人工私信，人数增长后无法稳定服务。

02 / 项目目标

不是简单“做一个网站”，而是建立可规模化的运营机制。

系统需要同时降低运营的人工作业量、保证数据不丢失，并让创作者能够自行确认投稿、积分、兑换和奖励进度。

GOAL 01

统一数据入口

将注册资料、作品、积分流水、订单与履约结果集中管理，以 Game UID 和 Account ID 建立稳定身份关系。

GOAL 02

建立月度闭环

让每个活动月都能够按固定流程完成开放、投稿、审核、结算、兑换、发奖和复盘。

GOAL 03

降低沟通成本

将常见查询转为创作者自主查看，并通过 MochiBot 完成必要的自动通知与逐人结算消息。

GOAL 04

支持规模增长

在创作者持续扩张后，仍能保持名单可筛选、操作可审计、结果可追踪、异常可恢复。

03 / 解决方案

以统一活动月为主线，连接创作者端和管理端。

我没有继续叠加更多人工表格，而是重新梳理完整业务链路：创作者负责提交和查询，管理员负责审核与履约，Supabase 保存业务事实，MochiBot 承担必要通知。

01

注册申请

统一收集身份、区服与履约资料。

02

人工审核

批准后激活账号并建立欢迎周边。

03

月度投稿

作品进入管理员指定的活动月份。

04

作品审核

按平台、数量和状态集中处理。

05

积分结算

通过 UID 导入确认后的算分结果。

06

个性化通知

每位创作者只收到自己的结算内容。

07

自主兑换

创作者查看余额并提交一种奖励。

08

奖励履约

发放结果公开，确认后完成扣分。

04 / 项目结果

从“靠人记住”升级为可持续复用的线上机制。

系统已经投入真实 KOC 运营，将原本分散的人工操作收拢为一条可查看、可复核、可追踪的完整链路，并具备继续扩大招募规模的基础。

100+创作者资料集中管理，注册与审核状态统一
1,700+单月作品链接进入统一投稿与审核流程
7社交平台作品使用同一套归集与筛选方式
3钻石、礼品卡与实体周边形成独立履约链路
RESULT 01

数据不再依赖多份表格

创作者、投稿、积分、兑换与发放状态围绕同一身份和活动月关联。

RESULT 02

创作者可以自主核对

作品是否提交成功、积分余额、订单和奖励结果均可在门户查看。

RESULT 03

运营动作可复用

筛选、批量审核、积分导入、通知和履约不再每月重新搭建流程。

RESULT 04

异常有记录可追踪

关键操作保留状态、失败原因与审计记录，降低重复发放和误操作风险。

05 / 个人贡献

从业务负责人到全栈开发者，独立推动项目落地。

我不仅负责把需求“做成页面”，而是从真实运营问题出发，完成业务建模、规则定义、系统开发、数据迁移、测试上线和持续迭代，对最终业务结果负责。

我解决了什么

把原本分散在 Discord 私信、Google Form、Excel 和人工台账中的工作，拆解为可执行的产品流程；明确活动月份、投稿状态、积分流水、等级进度、兑换窗口和奖励履约之间的关系，减少因口径不一致造成的遗漏与重复操作。

我如何落地

采用轻量架构降低维护成本：GitHub Pages 承载双前端，Supabase 保存业务数据并执行受控函数，Discord API 与 MochiBot 负责运营通知。借助 Codex 完成功能开发，同时通过真实业务场景反复验证和修正。
